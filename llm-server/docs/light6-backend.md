# 라이트 6회 호출 — LLM 서버 API와 백엔드 연동 명세 (초안)

**작성** 2026-10-14 · LLM 파트(윤세연) · **상태** 백엔드 검토 요청
**근거** 「라이트 뷰 LLM 호출 구조 — 데이터 흐름」(PM 확정안 10/14, 이하 34번) · 「코멘트 작성 가이드라인」(이하 31번) 2.2절 Q1·Q3, 1.2~1.4절 문장 규칙 · 23-타임아웃기준정리 v0.3
**LLM 서버 코드** 브랜치 `light-6call` — `app/light6.py`(프롬프트·검증), `app/light6_flow.py`(백엔드 흐름 참고 구현), `app/main.py`(엔드포인트)

## 1. 요약

- 34번대로 **단계를 잇는 것은 백엔드**다. LLM 서버는 단계마다 엔드포인트 하나씩, 모두 4개를 연다.
- 각 엔드포인트는 지금의 light·heavy 엔드포인트와 같은 규칙을 따른다. 검증을 통과하면 **200**, 통과하지 못하면 **502**(백엔드가 그 호출만 재요청), 입력 길이 초과는 **413**(재요청하지 않음), 요청 형식 오류는 **422**.
- **검증 ①②③의 내용 검사(정답 대조·금지 표현 등)는 LLM 서버가 한다.** 백엔드는 502를 받으면 재요청하고, 구조 검사(키·개수)와 조립만 한다. → 34번 2절의 "[백엔드] 검증" 위치를 이렇게 나누는 것을 제안한다(3절).
- JSON 키는 지금처럼 snake_case. null 필드는 생략해도 된다(백엔드 Jackson 설정 그대로).
- 기존 `POST /v1/comment/light`는 그대로 둔다. `LLM_LIGHT_MODE=six`로 켜면 6회 흐름을 **서버 안에서 순서대로** 실행한다. 백엔드 구현 전 연동 시험과 비교 측정용이다(3단계를 동시에 못 해서 느림).

## 2. 엔드포인트

### 2.1 1단계 판정 — `POST /v1/light/judge`

요청 — 후보 11개 × {지표, 값, Q1, Q3}. 값이 없는 지표는 `value`를 생략하거나 null로 보낸다(영역 '없음'). 순서는 상관없다(서버가 고정 순서로 맞춤).
```json
{"candidates": [
  {"stat": "delta_opener", "value": 0.36, "q1": -0.249, "q3": 0.171},
  {"stat": "delta_plonk", "q1": -0.122, "q3": 0.119},
  ...
]}
```
- Q1·Q3는 31번 2.2절(=「claude/21」 2.2절) **소수 셋째 자리 값 그대로**. LLM 서버 `config/light_quartiles.json`과 같아야 한다(34번 3.0절).
- 같은 stat 두 번, Q1 ≥ Q3 → 422.

응답 200 — 후보 고정 순서(opener · plonk · stride · inf_ds · app · weighted_app · vs_apm · cheese_index · strength_split · comeback · session_vs_slope) 중 요청에 있던 것만.
```json
{"judgments": [
  {"stat": "delta_opener", "zone": "높음", "deviation": 0.4},
  {"stat": "delta_plonk", "zone": "없음", "deviation": null},
  ...
]}
```
- 검증 ①: 모든 지표의 영역이 계산값과 같고 벗어난 정도가 ±0.1 안이어야 200. 하나라도 틀리면 502 → **판정만 재요청**. 모델 값을 서버 계산값으로 덮어쓰지 않는다(선정 주체 원칙).

### 2.2 2단계 선정 — `POST /v1/light/select`

요청 — 1단계 응답의 `judgments`를 **그대로** 넘긴다.
```json
{"judgments": [{"stat": "delta_opener", "zone": "높음", "deviation": 0.4}, ...]}
```
응답 200 — 우선순위 순. **3개보다 많을 수 있다 → 백엔드가 앞 3개만 쓴다**(34번 2절).
```json
{"stats": ["delta_app", "delta_opener", "delta_cheese_index"]}
```
- 검증 ②: 11개 키 안 · 서로 다름 · '없음' 아님인 것만 남긴다. 남은 것이 min(3, '없음' 아닌 지표 수)보다 적으면 502 → 선정 재요청.
- 모든 지표가 '없음' → 422(고를 수 없음).
- 서버는 목록을 정렬하지 않고 고정 순서로 모델에 준다. 선정 규칙(31번 2.2절)을 지켰는지는 검사하지 않는다(선정은 LLM — 34번 1절). 규칙 일치율은 측정 항목.

### 2.3 3단계 개별 코멘트 — `POST /v1/light/sentence` (선정된 3개 각각 1번)

```json
요청 {"stat": "delta_app", "value": 0.085, "zone": "높음"}
응답 {"stat": "delta_app", "sentence": "상대 대비 블록당 공격량(APP)에서 앞섭니다(+0.085)."}
```
### 2.4 3단계 기본 코멘트 — `POST /v1/light/summary` (1번)

```json
요청 {"items": [{"stat": "delta_app", "value": 0.085, "zone": "높음"}, ... 최대 3개]}
응답 {"light_summary": "…2~3문장…"}
```
- 개별 코멘트 결과를 받지 않는다 → **개별 3개와 기본 1개, 모두 4개를 동시에 보낼 수 있다**(34번 3절).
- `zone`은 받지만 문장 프롬프트에는 넣지 않는다. 10/14 실측에서 판정 라벨("보통")이 문장에 섞여 나왔기 때문이다.
- 검증 ③(31번 1.2·1.3·1.4): 입력에 없는 숫자, %·%p, 유형 규정("~형 플레이어"), 연승·연패·최근 N경기, 다른 유저와 비교, 판정 정보 노출, delta_*(역전 제외)에 비교 기준 표현 누락, strength_split·session_vs_slope에 "상대보다", 성향 지표에 우열 서술어, 방향 반대. 하나라도 걸리면 502 → **그 호출만 재요청**.

## 3. 검증을 어디서 하나 — 제안

| 지점 | 34번 | 제안 | 이유 |
|---|---|---|---|
| ① 판정 대조 | 백엔드 | **LLM 서버**(502) | 계산식·반올림(사사오입)·허용 오차를 한 곳에 둔다. 학습 데이터·측정 스크립트도 같은 코드를 쓴다 |
| ② 선정 구조 | 백엔드 | LLM 서버(502) + **백엔드는 앞 3개 자르기** | 지금 백엔드의 `validHighlights`·3개 자르기와 같은 역할 |
| ③ 문장 | 백엔드 | **LLM 서버**(502) | 한국어 금지 표현 목록·정규식을 Java로 다시 만들지 않아도 된다. 헤비도 이미 서버가 검사 후 502 |

백엔드가 따로 대조하고 싶으면 2.1의 계산식(34번 3.0절)으로 같은 결과가 나온다. 그래도 덮어쓰지 않고 재요청만 한다.

## 4. 백엔드 흐름 (34번 2·5절)

```
판정 ─(502면 판정만 재요청)→ 선정 ─(502면 선정만 재요청, 200이면 앞 3개)→ 개별 ×3 + 기본 ×1 동시 ─(502인 호출만 재요청)→ 조립
```
| 끝내 실패한 곳 | 응답 (34번 5절) |
|---|---|
| 판정 또는 선정 | 하이라이트 없이 응답 (기존 "총평만/0개" 처리와 같은 화면) |
| 개별 코멘트 1개 | 그 카드는 **수치만**(sentence 없음) — 프론트가 sentence null/빈 값을 처리해야 함 → **프론트 확인 필요** |
| 기본 코멘트 | 생략 — 지금은 light_summary가 있어야 200을 주는 로직(`hasSummary`)이 있어 바꿔야 함 |

- 큐: 4개 호출 모두 지금의 서버별 대기열(light 우선, 서버당 1건)에 넣는다. "시작한 라이트 요청의 다음 단계 우선"은 MVP 이후(34번 6절 5번).
- 3단계 4개는 라운드로빈으로 서버에 나눈다. 2대면 2개씩.
- `attempt_count`: 단계별 재요청 합계로 할지, 단계별로 나눠 줄지 백엔드·QA가 정한다.

## 5. 단계별 타임아웃 — 제안 (11번 실측 후 확정)

23번 2절 산출식 **(첫 토큰 2.2초 + max_tokens ÷ 49 tok/s) × 1.5** 를 단계별 max_tokens에 적용했다.

| 단계 | max_tokens | 산출 | 호출 1회 제안 |
|---|---|---|---|
| 판정 | 200 | (2.2 + 4.1) × 1.5 ≈ 9.4 | 10초 |
| 선정 | 24 | (2.2 + 0.5) × 1.5 ≈ 4.0 | 5초 |
| 개별 | 119 | (2.2 + 2.4) × 1.5 ≈ 6.9 | 7초 (heavy와 맞추면 10초) |
| 기본 | 160 | (2.2 + 3.3) × 1.5 ≈ 8.2 | 9초 |

- 정상 경로(재요청 없음, 서버 2대) 예상: 판정 + 선정 + 3단계 2회분. 실측 값은 `tools/measure_light6.py`의 "2대 환산" 열.
- 엔드포인트 상한(지금 40초)과 "남은 시간 ≥ 12초" 조건은 단계별로 다시 정해야 한다(34번 6절 4번, 8절).

## 7. 시험 방법

1. LLM 서버를 Mock으로 띄운다. `LLM_GENERATOR=mock python -m uvicorn app.main:app --port 9101`
2. 백엔드 단위 시험은 2절의 JSON 예시를 그대로 쓴다. Mock은 모델 없이 즉시 정답 형식으로 답한다.
3. 실제 모델 시험은 11·13번 서버를 `light-6call` 브랜치로 띄우고 같은 경로로 호출한다.
